Purpose

Let an adult record their own narration of any book from inside the mobile app, page by page, and have that recording become a selectable narration voice in the reader — with the existing karaoke-style word highlighting synced to their timing, not ElevenLabs'. A child then rereads the book as many times as they like in a familiar voice.

The whole feature is designed around one existing seam: the reader already highlights words from PageData.narrationTimestamps paired with PageData.narrationUrl. If a parent recording can produce those two values in the same shape, zero changes are needed in the highlight engine, overlay layout engine, or page renderer.

Problem

Today narration is generated server-side by admins: POST /api/admin/generate-narration calls ElevenLabs text-to-speech with timestamps, converts the returned character alignment into [{word,start,end}] via alignmentToWordTimestamps(), uploads the MP3 to the storia-storage bucket, and writes pages.narration_url + pages.narration_timestamps. The mobile reader reads those two columns and highlights word i while timestamps[i].start ≤ position ≤ timestamps[i].end.

Three gaps block a parent recording:

GapDetail
No capture pathThe mobile app has speech_to_text (for read-aloud practice) but no audio recorder, no mic permission strings, and no storage upload code anywhere in lib/src.
No timings for arbitrary audioThe TTS pipeline gets word timings for free because ElevenLabs generates the audio. A human recording arrives with audio only — timings must be derived by forced alignment against known text.
Narration is single-valuedpages.narration_url / narration_timestamps are one global track per page. Personal recordings are per-user, per-book, and must never overwrite the published narration or leak between accounts.

Also worth naming: the highlight index is positional. OverlayLayoutEngine assigns each rendered token a globalWordIndex counted across overlay elements in order; computeActiveWordIndex() returns an index into narrationTimestamps. If the recording's timestamp array has a different length or ordering than the page's rendered words, every highlight after the first mismatch is wrong.

Solution

Record per page on device → upload to the existing Next.js API → forced-align server-side against the page's own text → store a per-user narration track → reader substitutes it into PageData at load time.

parent (mobile) storia.kids API ElevenLabs / Supabase [Narration Studio] record page 3 ──► m4a ──► POST /api/narrations/pages ──► upload m4a ──► storia-storage bucket (record pkg, AAC) (Bearer supabase token, │ multipart file + trackId) └─► POST /v1/forced-alignment (file + page reference text) │ reference words ◄───────────────┘ words[{text,start,end}] (built from page.text_overlay, same order as globalWordIndex) │ ▼ user_narration_pages row { audio_url, word_timestamps, status } [Reader] GET /api/books/{id}/narrations ──► track + pages ──► PageData.copyWith( narrationUrl, narrationTimestamps) │ existing computeActiveWordIndex ◄┘ → highlighting, unchanged

Why this shape

  • Reuse the alignment converter, not the highlight engine. src/lib/elevenlabs.ts already owns CharacterAlignment → WordTimestamp[]. The forced-alignment endpoint returns the same character/word structure as TTS-with-timestamps, so the existing helper does the conversion.
  • Server-side alignment, always. ELEVENLABS_API_KEY and the Supabase service-role key must never ship in the app binary. The mobile client already talks to API_BASE_URL (https://storia.kids) with a Supabase bearer token via ChildProfileRepository; the same getAuthenticatedUser() dual-stack helper gates the new routes.
  • Per page, not per book. One recording per page means: no page-boundary detection, retake one page without redoing the book, short alignment jobs (seconds of audio), and a natural progress UI. Whole-book recording would need silence detection or manual page-turn markers — strictly more work for a worse retake story.
  • Reference text comes from the server's copy of the page, never from the client. The alignment text and the rendered words must come from one source of truth or the positional index drifts.
  • No reader-runtime surgery. Track selection resolves before Book reaches ReaderScreen: pages are rewritten with the parent's narrationUrl + timestamps. Everything downstream — page_audio.dart, AudioEngine, computeActiveWordIndex, OverlayLayoutEngine, buildWordToIndices — is untouched.
The load-bearing invariant: word_timestamps.length for a page MUST equal the number of rendered word tokens on that page, in render order. The backend enforces this by aligning against server-built reference words and, on any count mismatch, re-projecting aligner timings onto the reference tokens (or falling back to proportional timing) before persisting.

3. Forced alignment + projection

  • [x] Add forceAlign({audio, contentType, text}) to src/lib/elevenlabs.ts: multipart POST https://api.elevenlabs.io/v1/forced-alignment with file + text, header xi-api-key. Verify the current request/response contract and quota limits against ElevenLabs docs before coding.
  • [x] Prefer the response's word-level array; if only character alignment is returned, run it through the existing alignmentToWordTimestamps().
  • [x] In alignRecording.ts: if aligned word count === reference token count → status aligned, but rewrite each word field to the reference token (so display text always matches the page).
  • [x] If counts differ → project by monotonic index scaling onto reference tokens, status projected; if the aligner errors or returns nothing → fallbackTiming(), status fallback.
  • [x] fallbackTiming(tokens, durationMs): weight = token length + 1, plus a fixed extra weight for tokens ending in .?!,;:; distribute duration proportionally. Pure function, no I/O.
  • [x] Guarantee post-conditions before persisting: timestamps.length === tokens.length, monotonically non-decreasing start, start <= end, end <= durationSeconds. Throw (not silently persist) if violated.
// src/lib/narration/alignRecording.ts (shape)
export type AlignmentStatus = "aligned" | "projected" | "fallback";

export async function alignRecording(args: {
  audio: Buffer; contentType: string; tokens: string[]; durationSeconds: number;
}): Promise<{ timestamps: WordTimestamp[]; status: AlignmentStatus; loss?: number }> {
  try {
    const res = await forceAlign({ audio: args.audio, contentType: args.contentType,
                                   text: args.tokens.join(" ") });
    const words = res.words?.length ? res.words : alignmentToWordTimestamps(res.alignment);
    if (words.length === args.tokens.length) {
      return { status: "aligned", loss: res.loss,
               timestamps: words.map((w, i) => ({ ...w, word: args.tokens[i] })) };
    }
    return { status: "projected", loss: res.loss,
             timestamps: projectOntoTokens(words, args.tokens, args.durationSeconds) };
  } catch (err) {
    console.warn("[narration] forced alignment failed, falling back", err);
    return { status: "fallback",
             timestamps: fallbackTiming(args.tokens, args.durationSeconds) };
  }
}

Questionables

Open decisions carried by this plan. Each has a default assumption already baked into the phases above — override before Phase 1 if wrong.

Who can hear a recording — only the recorder's account, or the whole family/classroom?

Assumed: owner account only. Tracks are keyed to the Better Auth user.id, and every child profile under that account sees them (child profiles share the parent's session — there is no separate child auth). A teacher sharing one recording across many families' accounts would need a share/visibility column and a distribution mechanism; that is a genuinely different feature (moderation, revocation, storage attribution) and is deliberately out of scope. If teacher-sharing is the actual product goal, say so now — it changes the schema (add visibility + a grants table) but not the capture or alignment work.

Is ElevenLabs forced alignment the right aligner — cost, limits, latency?

Assumed yes, because the account, key, and character→word converter already exist in src/lib/elevenlabs.ts, and per-page audio is short (seconds). Verify current pricing, request-size limits, and the exact response schema against the docs during Phase 1 task 3 rather than trusting this document. Alternatives if it disappoints: Whisper with timestamp_granularities:["word"] plus text-anchored matching (more code, needs a second vendor), or shipping only the proportional fallback (free, visibly worse). The fallback path is built either way, so a vendor swap touches one file.

Per-page recording vs. record-the-whole-book-in-one-take?

Assumed per page. It removes page-boundary detection entirely, keeps alignment jobs short, and makes retakes cheap. The cost is a slightly more clinical recording experience (stop/start per page) versus reading a story straight through. If user testing says the stop/start breaks the reading flow, the upgrade is a continuous-record mode with a "next page" tap that records split points, then slicing server-side — same alignment core, new capture UI.

Should recordings work offline / be cached for repeat reads?

Assumed streamed from the public bucket URL, same as published narration today — no new caching layer. Repeat reads therefore need connectivity. If offline rereads matter (car rides, bedtime with bad wifi), the smallest upgrade is just_audio's LockCachingAudioSource for narration URLs, which also improves published narration. Deliberately not built now.

Child-safety: recorded audio is user-generated content in a kids' app.

Assumed acceptable because it is private to the recording account — nothing is shared, published, or discoverable by other users, so it is closer to a voice memo than to UGC. The moment sharing is added (see the first questionable), moderation, reporting, and retention policy become mandatory rather than optional. Storage bucket paths are namespaced by user id so a per-account purge is a single prefix delete.

Does the highlight look right when the reader's pace differs wildly from TTS?

Assumed yes for aligned status, since forced alignment is derived from the actual audio, not an assumed pace. The risk is concentrated in projected/fallback rows, where drift is proportional to how uneven the reading was. That is why status is persisted and surfaced in the studio with a retake nudge, and why alignment_loss is logged — the threshold for auto-suggesting a retake should be tuned from real data after launch, not guessed now.

What if the book's text is edited after a parent records it?

Assumed rare and handled by staleness detection, not re-alignment. Persist word_count per recorded page; at read time, if the page's current rendered word count differs from the recording's, keep playing the audio but treat the highlighting as untrusted for that page (highlight off, audio on) and flag a retake in the studio. Silently misaligned highlighting is worse than none.

Notes

The one insight that shrinks this feature

The reader's karaoke highlighting has no notion of "who is speaking". page_renderer.dart calls computeActiveWordIndex(page.narrationTimestamps, widget.narrationPosition) and hands the index to OverlayLayoutEngine, which matches it against each token's globalWordIndex. Feed it a different narrationUrl + a matching timestamp array and the feature is done. Every phase above exists only to produce that array safely. Resist any temptation to add a parallel "custom narration" playback path in AudioEngine — that would fork behavior that currently has exactly one implementation.

Rejected approaches

  • On-device alignment via speech_to_text. The app already depends on it, so it's tempting — but platform recognizers stream hypotheses, not reliable per-word timestamps against a known script, and behavior diverges sharply between iOS and Android. It would produce exactly the drifting highlight this feature exists to avoid.
  • Manual tap-to-sync ("tap each word as you read"). Zero backend cost, but an unusable authoring experience for a parent at bedtime, and it produces worse timings than an aligner.
  • Writing into pages.narration_url / narration_timestamps. Would let the reader work with no code changes at all — and would let one parent overwrite the published narration for every user. Non-starter.
  • A new Supabase Edge Function instead of Next.js routes. The repo has no supabase/functions directory, no deploy pipeline for one, and the auth helper (getAuthenticatedUser) plus the alignment converter both live in the Next app. Adding a second backend runtime for one endpoint is unnecessary.
  • Direct client→Supabase Storage upload with RLS. Saves one hop, but the alignment step must happen server-side anyway (API key), and the current mobile app has no storage-upload code or bucket policies at all. Uploading through the API keeps one code path and one auth model.

Cross-repo coordination

Phase 1 ships to storia (web/API) and must be deployed before Phase 2 is useful on a device — mobile talks to API_BASE_URL, defaulting to https://storia.kids. For local development, point the mobile .env API_BASE_URL at the dev machine's LAN address and run npm run dev (which prepares the Dockerized Postgres on :5433 first). Phases 2 and 3 are mobile-only and can land in one release.

Word-order parity: the thing most likely to break

Two tokenizers must agree forever: buildPageReferenceWords() (TypeScript, server) and the token split inside overlay_layout_engine.dart / page_words_indexer.dart (Dart, client). They are in different repos and different languages, so drift is a matter of when, not if. Mitigations, in order of value: (1) the shared fixture asserted in both test suites; (2) persisting word_count and refusing to highlight when it disagrees with the rendered count at read time; (3) a comment in each tokenizer naming the other. Note that page_words_indexer.dart additionally normalizes tokens via normalizeWordToken for word-help lookups — the reference builder must NOT normalize; it needs raw display tokens in raw order.

Scope explicitly left out

  • Sharing recordings between accounts, classrooms, or family members.
  • Recording from the web editor (this is a mobile-first feature; the backend routes are platform-agnostic if that changes).
  • Audio cleanup: trimming leading/trailing silence, noise reduction, loudness normalization.
  • Mixing parent narration with soundscapes at different levels — existing narration/soundscape volume controls apply unchanged.
  • Per-word pronunciation audio from the parent's voice (the book_pronunciations pipeline stays TTS-driven).
